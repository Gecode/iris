The `gecode-iris` package binds the Rust reference implementation of Iris;
import it as `gecode_iris`. Parsing, reading, errors, JSON and dzn all come
from the Rust reader, so Python reads every input exactly as the
[CLI](/tools/cli/) does. The package needs Python 3.10 or newer and includes
type stubs. The [Python API reference](/using/python/api/) lists every public
class and method.

## Parse a reader spec and read input

The examples on this page are in
[`python/examples`](https://github.com/Gecode/iris/tree/main/python/examples),
and a test runs each one against the built package and compares its output.
They read files from the format library, so run them from the root of an
Iris checkout.

<CheckedExample id="python-read" title="read.py" />

`Spec.parse` parses and checks a reader spec given as `str` or `bytes`. The
declaration reads `n`, then a row of `n` integers. `spec.read` reads input
bytes; the origin names, such as `example.iris` and `input.txt`, appear in
error messages. A `Spec` can read any number of inputs, and threads can share
it.

## Read files, instances and parameters

`Spec.load` reads a reader spec file. `spec.read` and `spec.catalog` take a
path as `str` or `os.PathLike`; a `str` is always a path, never input text.

<CheckedExample id="python-files" title="files.py" />

`spec.catalog` lists the instances in a file as data. The `instance` parameter
selects one instance during a read, by name or by its number, counting from
1. Parameter values are strings, as the
[Specification](/specification/0.1/09-params-and-instances/) defines; pass
`{"instance": "2"}`, not `{"instance": 2}`.

## Access data

`data.entries` lists the entries in the order the reader spec defines them.
`data[name]` returns an entry's value as Python objects: an `int`, `float` or
`str` at depth 0, and nested lists at greater depths. Each access copies the
value.

<CheckedExample id="python-access" title="access.py" />

`data.ints(name, *path)` returns the integer row that the index path selects.
A negative index counts from the end of its row, as in a list. `data.to_dict()`
returns every entry. An unknown name raises `KeyError`, an index outside its
row raises `IndexError`, and a selection of the wrong type raises
`TypeError`.

When numpy is installed and an array is rectangular, `data.array(name, *path)`
returns a `numpy.ndarray` of `int64`, `float64` or `str_` elements, with one
dimension per level. Otherwise it returns the same nested lists as
`data[name]`, so check the type before using numpy methods:

<CheckedExample id="python-arrays" title="arrays.py" />

## Handle errors

A language error raises `gecode_iris.Error`. Its `code` is the stable
[error code](/specification/0.1/errors/), and `line`, `column` and `origin` give
the input location when there is one, and otherwise the reader spec location.
Any of them can be `None`. `path` is the record path of a failed check over
records. `str(error)` is the same diagnostic that the CLI prints, and
`error.to_json()` returns the canonical error document.

<CheckedExample id="python-errors" title="errors.py" />

Host failures raise built-in exceptions and have no error code: a missing file
raises `FileNotFoundError`, and other file access failures raise other
`OSError` subclasses. Python types that the API does not accept, such as an
integer parameter value, raise `TypeError`.

## Build a reader spec

`gecode_iris.build` writes a reader spec from Python. Every statement that
defines an entry returns a typed handle, and `data[handle]` returns the entry
with the handle's type, so a type checker such as pyright or mypy sees `int`
for `n_jobs` and `list[list[int]]` for `machine`, and flags a misspelled handle.
A builder adds no features of its own: `build()` prints Iris text and parses it
as `Spec.parse` does, so the language's checks decide what is valid, and
`source()` returns the text.

The examples below are in
[`python/examples`](https://github.com/Gecode/iris/tree/main/python/examples),
one builder for each format in the [format library](/formats/). A test reads
every case of each format through its builder and compares the data or the
error with the case's expected results, then runs each program and compares its
output with the output shown here. The programs read files from the format
library, so run them from the root of an Iris checkout, as in
`python python/examples/build_jobshop.py`.

### The job shop builder

This builder writes the [job shop](/formats/job-shop/) reader spec. `main` reads
an instance selected by name, then a file whose check fails.

<CheckedExample id="python-build_jobshop" title="build_jobshop.py" />

Blocks are `with` statements: `b.instances()`, `i.sections()` and
`a.repeat(n_jobs)` each open a scope, and the statements inside the `with` go
into it. A pattern is a tuple of text and handles, as in
`(n_jobs, " ", n_machines)`. `job.record` is the handle of each record of a
repeat, which the builder names itself with `each record_1`: `jobs[machine]`
looks up a field and prints `record_1.machine`, and
`ib.sum(jobs, lambda j: ...)` prints a comprehension over the records.
`job.as_name("jobs")` names the list of records, as in `repeat n_jobs as jobs`,
for error messages.

Python operators build expressions: `<=`, `==`, `+` and `*` work on handles as
they do in Iris, and `&`, `|` and `~` stand for `&&`, `||` and `!`, since
Python's `and`, `or` and `not` cannot be overloaded. A range is
`ib.int_range(0, below=n_machines)` for Iris `0..<n_machines`, or
`ib.int_range(0, n)` for `0..n`.

### Typed data

`data[handle]` returns the Python type of the entry's value type and depth: an
`int` for `n_jobs`, a `str | None` for the `name`, which only some files give,
and a `list[list[int]]` for `machine` and `duration`, which have one value per
step of each job. A handle names its entry, value type and depth, so a lookup
cannot read the wrong entry, and a handle from a different spec whose entry has
another type raises `TypeError` instead of returning the wrong type.

Collecting the handles in a `NamedTuple` with the spec, as `Jobshop` does, gives
the rest of a program one typed object to read with.

### Errors name your code

Every statement records the line of the call that wrote it. When a check fails
while reading, the error has the input location, and `error.call_site` names the
`i.check` line in `build_jobshop.py`, with its file name and function. A
`gecode_iris.build.BuildError` from `build()` has the same call site. A
statement in a helper function records the line in the helper, unless the
helper has the `@ib.track_caller` decorator, as `clue_lines` below does.

### A helper used twice

A function that takes a scope and returns handles is a reusable piece of a
reader spec. The nonogram builder reads the clues of the rows and the columns
with one helper, and builds two pairs of checks with two expression helpers.

<CheckedExample id="python-build_nonogram" title="build_nonogram.py" />

A builder rejects a second definition of a name, so a helper called twice by
mistake fails `build()` instead of quietly replacing an entry. That is why
`clue_lines` takes the entry name from its caller. The TSPLIB builder below
uses the same idea for its two coordinate sections.

### Typed handles for a text spec

A reader spec written as an `.iris` file has no builder, but `iris gen --lang
python SPEC` prints a module with a typed handle for each of its entries:

<CheckedExample id="python-view" />

Save the output as a module, such as `jobshop_view.py`, and read data with
`data[jobshop_view.machine]` as with a builder's handles; a type checker sees
the same types. `ib.declared` makes each handle from the entry's name and its
handle type. An entry whose value type or depth differs between the places that
define it gets `ib.DynField`, which returns any value or `None`. A declared
handle reads data from any spec with that entry, and a lookup checks the value
type and depth, but no builder accepts it, since no builder made it.
