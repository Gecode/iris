Rust is the reference implementation of Iris. The `gecode-iris` crate
re-exports the public reader API from `gecode-iris-core`; import it as `gecode_iris`.
It returns named, typed entries, including arrays whose rows have different lengths.

## Add the dependency

Use Rust 1.88 or newer. Add this to your application's `Cargo.toml`, or run
`cargo add gecode-iris`:

<CheckedExample id="rust-dependency" title="Cargo.toml" />

Package versions and language versions are separate; the current Rust packages are
0.1.0 and implement Iris 0.1.

## Parse once, read input, borrow a row

Put this in your application's `src/main.rs`. It follows the umbrella
crate's doc-tested example, wrapped in `main`.

<CheckedExample id="rust-example" title="src/main.rs" />

`Spec::parse` validates the reader spec. The declaration reads `n`, then a row
of `n` integers. `Spec::read` reads input bytes using caller parameters; an empty
`Params` supplies none. Origin names such as `example.iris` and `input.txt`
appear in diagnostics.

`Data::int` returns a scalar. `Data::ints` borrows an integer row without copying
it. The empty index path selects the whole one-dimensional row here; for a column
of rows, the path selects a row. The returned `Data` owns its entries and does
not borrow the original input bytes, so the same `Spec` can read another input.

To run the original example from the Iris checkout, use its `rust/` directory:

## Files, parameters, and output

`Spec::read_path` reads a file with caller parameters. `Spec::catalog` and
`catalog_path` traverse a multi-instance file and return catalog data.
The `instance` parameter selects an instance during a read by ordinal or name;
see [parameters and instances](/specification/0.1/09-params-and-instances/).

`Data::entries` visits entries in definition order. `Data::value` selects a
borrowed value by name and index path. `to_json` and `to_dzn` return buffered
output; `write_dzn` writes to an `io::Write` destination. A stream error can leave
partial bytes in that destination. The [data model](/specification/0.1/03-data-model/)
and [dzn appendix](/specification/0.1/appendix-b-dzn/) define the representations.

## Handle failures

Parsing and reading return `Failure`. `Failure::Language` contains an error
with a stable [language code](/specification/0.1/errors/), source locations and,
when applicable, a record path. Work-budget exhaustion is a language failure
([`E-BUDGET`](/specification/0.1/errors/#e-budget)). `Failure::Host` covers host
failures such as file acquisition or cancellation. `Failure::Unsupported`
identifies an implementation feature that has not been implemented.

After a successful read, typed lookup returns `AccessError` for an unknown name,
invalid index path or incompatible requested type. These are host API usage
errors. `Failure`, `HostError` and `AccessError` are non-exhaustive; matching their
variants requires a fallback arm.

For more detail, read the
[umbrella crate source](https://github.com/Gecode/iris/blob/main/rust/gecode-iris/src/lib.rs)
and [core API guide](https://github.com/Gecode/iris/blob/main/rust/iris-core/README.md).
Publication on docs.rs is planned; until then, `cargo doc` in the workspace
builds the API documentation locally.

## Build a reader spec in code

`gecode_iris::build` writes a reader spec from Rust calls. Every statement that
defines an entry returns a typed handle, so a misspelled entry or a wrong value
type fails when the program compiles, not when data is read. A builder adds no
features of its own: `build()` prints Iris text and parses it with `Spec::parse`,
so the language's checks decide what is valid, and `source()` returns the text.

The examples below are in
[`rust/gecode-iris/examples`](https://github.com/Gecode/iris/tree/main/rust/gecode-iris/examples),
one builder for each format in the [format library](/formats/). A test reads every
case of each format through its builder and compares the data with the case's
expected results, then runs each program and compares its output with the
output shown here. The programs read files from the format library, so run them
from the root of an Iris checkout, as in
`cargo run --manifest-path rust/Cargo.toml --example jobshop`.

### The job shop builder

This builder writes the [job shop](/formats/job-shop/) reader spec. `main` reads
an instance selected by name, then a file whose check fails.

<CheckedExample id="rust-build-jobshop" title="jobshop.rs" />

Blocks are closures that take the open scope and return the handles defined in
them. A capture is declared before the pattern that binds it, so `pattern!` can
interpolate it the way `format!` interpolates a variable. `job.record()` is the
handle of a repeat's records: `job.get(machine)` prints `job.machine`, and
`sum_over(job, ...)` prints a comprehension over the jobs. The builder names
records itself; `as_name("jobs")` gives the records a name for error messages.

Rust's `a..b` excludes `b`, so it prints as Iris `a..<b`, and `a..=b` prints as
Iris `a..b`. A handle or a host constant beside another bound needs `.ex()`, as
in `lit(0)..n_machines.ex()`.

### Typed data

`data.get(handle)` returns the Rust type of the entry's value type and depth: an
`i64` for `n_jobs`, an `Option<&str>` for the `name`, which only some files
give, and rows of `&[i64]` for `machine` and `duration`, which have one value
per step of each job. These are borrowed views of the data, without copies, and a lookup through
a handle cannot fail on a name or a type.

### Errors name your code

Every statement records the line of the call that wrote it. When a check fails
while reading, the error shows the input line, the line of the built text
(`spec: builder.iris:17`) and a `call site:` line that names the `distinct`
check in `jobshop.rs`. A `BuildError` from `build()` has the same call site
line. A statement in a helper function records the line in the helper, unless
the helper has `#[track_caller]`, as `clue_lines` below does.

### A helper used twice

A function that takes a scope and returns handles is a reusable piece of a
reader spec. The nonogram builder reads the clues of the rows and the columns
with one helper, and builds two pairs of checks with two expression helpers.

<CheckedExample id="rust-build-nonogram" title="nonogram.rs" />

A builder rejects a second definition of a name, so a helper called twice by
mistake fails `build()` instead of quietly replacing an entry. That is why
`clue_lines` takes the entry name from its caller. The TSPLIB builder below
uses the same idea for its two coordinate sections.
