The `gecode-iris` npm package runs the Rust reference implementation of Iris,
compiled to WebAssembly. Parsing, reading, errors, JSON and dzn all come from
the Rust reader, so the package reads every input exactly as the
[CLI](/tools/cli/) does. The package is ESM only, includes TypeScript
declarations, and runs in Node 22.12 or newer, browsers, Cloudflare Workers and
other edge runtimes.

## Parse a reader spec and read input

The examples on this page are in
[`typescript/examples`](https://github.com/Gecode/iris/tree/main/typescript/examples).
A test type-checks every one against the built package, runs each one that
Node can run, and compares its output. They read files from the format
library, so run them from the root of an Iris checkout.

<CheckedExample id="typescript-read" title="read.ts" />

`Spec.parse` parses and checks a reader spec given as a string or a
`Uint8Array`. The declaration reads `n`, then a row of `n` integers.
`spec.read` reads input from a string or a `Uint8Array`; the origin names, such
as `example.iris` and `input.txt`, appear in error messages. A `Spec` can read
any number of inputs.

## Choose a runtime

Every entry point loads the WebAssembly module before an importing module
runs, so `Spec.parse` works at the top level of your module, with no `await`
and no setup call. The package's export conditions pick the entry point for
your runtime.

In Node, `import` loads the package synchronously, as in the example above.
`require()` works too, in Node 22.12 or newer:

### Inline

`gecode-iris/inline` embeds the module in JavaScript and compiles it
synchronously, so it needs no file access, `fetch` or bundler support. It works
wherever WebAssembly can be compiled from bytes, but not in workerd, and it is
about a third larger than the `.wasm` file.

## Read files, instances and parameters

The package reads strings and bytes, not paths, so it runs where there is no
file system. In Node, read the files with `node:fs` and pass the paths as
origins:

<CheckedExample id="typescript-files" title="files.ts" />

`spec.catalog` lists the instances in an input as data. The `instance`
parameter selects one instance during a read, by name or by its number,
counting from 1. Parameter values are strings, as the
[Specification](/specification/0.1/09-params-and-instances/) defines; pass
`{ instance: "2" }`, not `{ instance: 2 }`. `params` also accepts an iterable
of `[name, value]` pairs, such as a `Map`.

## Access data

`data.entries` lists the entries in the order the reader spec defines them,
each with its name, value type and depth. `data.entry(name)` returns one entry,
or `undefined`, and `data.has(name)` tests for it.

<CheckedExample id="typescript-access" title="access.ts" />

A path is an array of indices counted from 0. `data.size(name, path)` returns
the length of the array that the path selects. `data.int`, `data.float` and
`data.string` return a scalar, and `data.ints`, `data.floats` and
`data.strings` return a row. `data.value(name, path)` returns a scalar or
nested arrays, whose rows can have different lengths, and `data.toObject()`
returns every entry. Each call returns a copy, and `Data` needs no freeing.

An unknown entry or an index outside its array throws `RangeError`, and a
selection of the wrong value type or depth throws `TypeError`.

## 64-bit integers

Iris integers are signed 64-bit, and a JavaScript `number` holds integers
exactly only up to `Number.MAX_SAFE_INTEGER` (2<sup>53</sup> − 1). The
accessors that return `number` throw `RangeError` for a larger value instead
of rounding it. `data.bigInt`, `data.bigInts`, which returns a
`BigInt64Array`, and the `{ bigint: true }` option of `value` and `toObject`
are always exact. Floats are always `number`.

<CheckedExample id="typescript-integers" title="integers.ts" />

## JSON and dzn

`data.toJSON()` returns the canonical JSON document and `data.toDzn()` the
MiniZinc data of the [dzn appendix](/specification/0.1/appendix-b-dzn/). Both
end in a newline.

<CheckedExample id="typescript-output" title="output.ts" />

`JSON.stringify(data)` calls `toJSON` and so encodes the document as one JSON
string; use `data.toJSON()` directly.

## Handle errors

A language error throws `IrisError`, a subclass of `Error`. Its `code` is the
stable [error code](/specification/0.1/errors/) and `message` the message
without a location. `inputLocation` and `specLocation` are each
`{ origin, line, column }` or `null`, and any of their fields can be `null`.
`context` says what was being read, and `recordPath` gives the record indices
of a failed check over records. `diagnostic` is the text that the CLI prints,
and `error.toJSON()` returns the canonical error document.

<CheckedExample id="typescript-errors" title="errors.ts" />

Host failures throw built-in errors and have no error code. A string with a
lone surrogate, a parameter value that is not a string, or a disposed spec
throws `TypeError`. Data beyond the limits of the package's 32-bit transfer
format throws `RangeError`, and other host failures throw `Error`.

A trap in the WebAssembly module, which only a bug in the package can cause,
throws `IrisInternalError`. It is not an `IrisError`, and its `cause` is the
original `WebAssembly.RuntimeError`. The package replaces the WebAssembly
instance after a trap, so later calls work, including calls on specs parsed
earlier.

## Budgets and deadlines

The language's fixed [work budgets](/specification/0.1/10-work-budgets/)
bound every read. A read that exhausts one throws `IrisError` with the code
`E-BUDGET`. The package has no budget settings.

<CheckedExample id="typescript-budget" title="budget.ts" />

Calls into WebAssembly are synchronous and cannot be interrupted on their own
thread. For a wall-clock deadline, read in a worker and terminate it when the
deadline passes. In Node, use `node:worker_threads`; in a browser, use a Web
Worker the same way.

<CheckedExample id="typescript-deadline-worker" title="deadline-worker.ts" />

<CheckedExample id="typescript-deadline" title="deadline.ts" />

`readWithDeadline` starts `deadline-worker.ts` by its URL. Node 22.18 and
newer run TypeScript directly; if you compile to JavaScript, point the URL at
the compiled file.

## Build a reader spec

`gecode-iris/build` writes a reader spec from TypeScript. Every statement that
defines an entry returns a typed handle, and `read` returns each entry with the
type of its handle: a `number` for `n_jobs` and a `number[][]` for `machine`. A
builder adds no features of its own: it prints Iris text and parses it as
`Spec.parse` does, so the language's checks decide what is valid, and `source`
holds the text. Like the package itself, `gecode-iris/build` has `inline` and
`manual` entry points.

The builders below are in
[`typescript/examples`](https://github.com/Gecode/iris/tree/main/typescript/examples),
one for each format in the [format library](/formats/), each with a `main`
that reads a case when Node runs the file. A test reads every case of each
format through its builder and compares the data or the error with the case's
expected results, and the examples test runs each file and compares its output
with the output shown here.

### The job shop builder

This builder writes the [job shop](/formats/job-shop/) reader spec, and the
program reads an instance selected by name, then a file whose check fails:

<CheckedExample id="typescript-build-jobshop" title="build-jobshop.ts" />

`spec("jobshop", (b) => ...)` builds the spec of a format. Blocks take a
callback, which receives the block's scope: `b.instances`, `i.sections`,
`s.arm` and `r.repeat` each open one, and the statements the callback adds go
into it. Each block returns what its callback returns, so the handles leave
the blocks as objects to destructure. `` p`${nJobs} ${nMachines}` `` is a
pattern with entries in its placeholders. A range is `range(0).below(nMachines)`
for Iris `0..<n_machines`, `range(0, n)` for `0..n` and `atLeast(1)` for
`1..`.

`r.record` is the handle of each record of a repeat: `job.get(machine)` looks
up a field, and `sum(job, (j) => ...)` writes a comprehension over the
records. `r.asName("jobs")` names the list of records, as in
`repeat n_jobs as jobs`, for error messages. Methods build expressions, such
as `nJobs.le(...)`, `a.and(b)` and `a.not()`, and `gecode.intMax` is Gecode's
largest integer.

### Typed data

`read` returns an object with the handles that the callback returned, each
typed by its handle: a `number` for `nJobs`, `string | undefined` for `name`,
which only some files give, and `number[][]` for `machine` and `duration`. A
handle names its entry, value type, depth and presence, and reading checks
them. For integers beyond `Number.MAX_SAFE_INTEGER`, read with `jobshop().spec`
and use `data.get(handle, { bigint: true })`, which gives `bigint`s.

### Errors name your code

Every statement records the line that calls it. When a check fails while
reading, the `IrisError` has the input location, and `error.callSite` names
the line of the check in `build-jobshop.ts`. A `BuildError` from a builder has
the same call site. A statement in a helper function records the line in the
helper, unless the helper is wrapped in `trackCaller`, which makes its
statements record the helper's caller, as `clueLines` below does.

### A helper used twice

A function that takes a scope and returns handles is a reusable piece of a
reader spec. The nonogram builder reads the clues of the rows and the columns
with one helper, and builds two pairs of checks with two expression helpers.

<CheckedExample id="typescript-build-nonogram" title="build-nonogram.ts" />

A builder rejects a second definition of a name, so a helper called twice by
mistake fails instead of quietly replacing an entry. That is why `clueLines`
takes the entry name from its caller. The TSPLIB builder below uses the same
idea for its two coordinate sections.

### Typed handles for a text spec

A reader spec written as an `.iris` file has no builder, but
`iris gen --lang typescript SPEC` prints a module with a typed handle for each
of its entries:

<CheckedExample id="typescript-view" />

Save the output as a module, such as `jobshop-view.ts`, import it with
`import * as jobshop from "./jobshop-view.ts"`, and read data from
`Spec.parse` with `data.get(jobshop.machine)`, which returns a `number[][]`.
The module imports only the `Handle` type, so it adds nothing to a bundle but
the handles. An entry whose value type or depth differs between the places
that define it gets a handle with the value type `"dyn"`, which returns a
`Value | undefined`.

## Release memory early

Only a `Spec` holds WebAssembly memory, and garbage collection releases it. To
release it earlier, declare the spec with `using`, or call
`spec[Symbol.dispose]()`. Calling `free()` is never required.
